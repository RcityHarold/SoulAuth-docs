# 为什么是 SoulAuth

身份提供方不缺。这里说清楚这一个为什么存在，以及你为什么可能不需要它。

## 它唯一不一样的地方

任何身份系统都能给机器人一个账户。建个用户、编个邮箱、设个口令、丢进一个组。能用。

它失效于有人问出一个系统答不上来的问题：

> 这个动作发生在 03:14。是谁做的？

诚实的答案通常是*两年前某人建的一个服务账号，密码在某条 Slack 消息里*。
那不是一个主体——那是一个挂了行记录的共享秘密。

SoulAuth 让非人主体成为**独立主体**。它有自己的 `ActorIdentity`，持有自己的密钥，
靠对挑战签名来证明自己。**没有邮箱、没有口令、背后也没有人类账户**——
而且一致性套件会断言这条认证路径根本不碰人类账户结构。
<Status kind="tested" guard="conformance::a6" />

这就是全部的差异化。除此之外，它是一个称职、平平无奇的 OpenID Connect 提供方
——而它本来就该是。

## 那几个对象为什么要分开

「机器人配个账户」这套之所以会塌，是因为它把需要各自独立变化的东西合并了：

| | |
|---|---|
| **身份** | 这是谁，持久地 |
| **账户** | 一个**人**怎么管理自己的登录 |
| **凭证** | 此刻能拿什么证明 |

身份并进账户，非人主体就必须伪造人类属性才能存在。身份并进凭证，
轮换一次密钥就产生一个新主体——归因恰好在你最需要它的时候断掉。

[完整模型 →](/zh/concepts/actor-identity-model)

## 它负责什么

认证，以及到此为止。认证成功产出的是一句关于**是谁**的陈述。
它不授予任何应用权限、治理地位或行动资格。

这条边界不是以后要放开的限制，它正是那个答案值得信任的原因。
[身份与权限的边界 →](/zh/spec/identity-vs-authority)

## 它不是什么

- **不是你业务规则的授权引擎。** 它回答「是谁」，不回答「可不可以」。
  它对自己的控制平面有 RBAC，不是对你的。
- **不是 Agent 框架。** 它认证 Agent，不运行、不编排、不推理它们。
- **不是记忆或推理系统。** 在 Soulseed 部署里，canonical actor 由别处定义；
  SoulAuth 持有的是引用，不是定义。
- **不是计费系统。** 遗留 user 行上确实有个会员字段，而它不该在那儿——
  见[项目状态](/zh/project/status)。
- **不是托管服务。** 你自己跑。
- **没有任何认证资质。** 没有标准组织认证过它的任何部分，自我声明也不构成认证。

## 什么时候该用别的

把这件事说具体，比列一堆功能有用：

**用托管服务**（Auth0、Clerk、WorkOS）——如果你不想运维一个身份服务。
这东西是一个二进制加一个数据库，需要你持续跑着、打补丁、做备份。

**用 Keycloak 或 Ory**——如果你需要经过认证的 OIDC 符合性、SAML，
或者一个现成的集成生态。SoulAuth 认真实现了授权码流程，此外不声称任何东西。

**用 better-auth 或 Lucia**——如果你要的是一个 TypeScript 应用内部的认证库，
而不是一个多应用共同对接的独立服务。

**用 SoulAuth**——如果你的系统里非人主体需要一等身份，而且你希望文档里每一句
声称都能指出撑住它的那条测试。

## 你实际拿到什么

一个 Rust 二进制加 SurrealDB。标准 OpenID Connect。一份由测试套件对着运行代码
核对的机器可读契约——所以本站的参考页是从它渲染出来的，不是手写的。

以及一份关于「什么还没做完」的如实交代：[读数](/zh/project/status)里列着十条
已经写好、能跑、而当前实现还达不到的不变式，每条都写了原因。
