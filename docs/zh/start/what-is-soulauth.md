# 为什么是 SoulAuth

可选的身份提供方已经很多。本页说明 SoulAuth 为什么还要存在，
以及在哪些情况下它并不适合。

## 唯一的差异

给机器人一个账户，在任何身份系统里都不难：创建用户，分配邮箱，设置口令，
加入某个组。这套做法能够正常工作，直到有人提出系统回答不了的问题：

> 这个操作发生在 03:14。是谁做的？

诚实的答案往往是*两年前某人创建的服务账号，口令在一条 Slack 消息里*。
那不是一个主体，而是一个附带了记录行的共享秘密。

SoulAuth 让非人主体成为**独立主体**：拥有自己的 `ActorIdentity`，持有自己的密钥，
通过对挑战签名来证明自己。**没有邮箱，没有口令，背后也不存在人类账户。**
一致性套件会断言这条认证路径完全不涉及人类账户结构。
<Status kind="tested" guard="conformance::a6" />

差异仅此一处。除此之外，SoulAuth 是一个称职而平常的 OpenID Connect 提供方，
而它本就该如此。

## 这些对象为什么要分开

「给机器人配个账户」之所以行不通，是因为这套做法把三样需要各自独立变化的东西
合并到了一起：

| | |
|---|---|
| **身份** | 这是谁，且持久不变 |
| **账户** | 一个**人**如何管理自己的登录 |
| **凭证** | 此刻能用什么来证明 |

身份并入账户，非人主体就必须伪造人类属性才能存在。身份并入凭证，
轮换一次密钥便产生新的主体，归因恰好在最需要它的时刻断裂。

[完整模型 →](/zh/concepts/actor-identity-model)

## 职责范围

只做认证，到此为止。认证成功产出的是一句关于**是谁**的陈述，
不授予任何应用权限、治理地位或行动资格。

这条边界不是留待日后放开的限制。恰恰相反，它正是那个答案值得信任的原因。
[身份与权限的边界 →](/zh/spec/identity-vs-authority)

## 不属于职责范围的

- **不是业务规则的授权引擎。** 它回答「是谁」，不回答「可不可以」。
  其中的 RBAC 只治理 SoulAuth 自身的控制平面。
- **不是 AI 主体框架。** 它认证 AI 主体，不运行、不编排、也不推理它们。
- **不是记忆或推理系统。** Soulseed 部署中的 canonical actor 由别处定义，
  SoulAuth 持有的是引用，而不是定义。
- **不是计费系统。** 遗留的 user 行上确实存在一个会员字段，而它本不该在那里，
  见[项目状态](/zh/project/status)。
- **不是托管服务。** 需要自行部署与运维。
- **不具备任何认证资质。** 没有标准组织认证过它的任何部分，自我声明也不构成认证。

## 什么情况下应当选择别的方案

把这一点讲具体，比罗列功能更有用。

**不打算运维身份服务，选托管方案**（Auth0、Clerk、WorkOS）。SoulAuth 是一个二进制
加一个数据库，需要持续运行、打补丁、做备份。

**需要经过认证的 OIDC 符合性、SAML，或成熟的集成生态，选 Keycloak 或 Ory。**
SoulAuth 认真实现了授权码流程，此外不作任何声称。

**只需要单个 TypeScript 应用内部的认证库，选 better-auth 或 Lucia。**
它们要解决的不是「多个应用对接同一个独立服务」这个问题。

**系统中的非人主体需要一等身份，选 SoulAuth。** 如果同时希望文档里每一句声称
都能指出撑住它的那条测试，那就更是如此。

## 实际交付的内容

一个 Rust 二进制，加一个 SurrealDB。标准的 OpenID Connect。一份由测试套件对照
运行代码逐条核对的机器可读契约，本站的参考页正是从它渲染出来的，而非手写。

以及一份关于「什么尚未完成」的如实交代：[一致性读数](/zh/project/status)中列出了
十条已经写好、能够运行、而当前实现尚未满足的不变式，每一条都写明了原因。
