# SoulAuth 是什么

SoulAuth 是一个**认证服务**：单个 Rust 二进制，后面接一个
[SurrealDB](https://surrealdb.com/) 实例，替你运行的其它一切回答
*「这个请求是谁发的？」*。

它说 [OpenID Connect](https://openid.net/developers/how-connect-works/)，
所以接入方不需要了解 SoulAuth 本身。它们对着一个标准端点说标准协议，
在本地验一下签名，然后继续干自己的事。

## 一句话版本

> SoulAuth 回答**这是谁**。它刻意不回答**他可以做什么**。

后半句不是缺失，是设计。理由写在
[在 Soulseed 生态里的位置](./soulseed-ecosystem)，
在你把 SoulAuth 接进任何授权判断之前值得先读。

## 你拿到什么

跑起 `soulauth`，你立刻拥有：

| 能力 | 具体是什么 |
| --- | --- |
| **注册与登录** | 邮箱 + 密码，Argon2 哈希，最小长度可配，邮箱验证可选。 |
| **第三方登录** | Google 与 GitHub，按 provider 隔离 —— 数字 id 为 `4001` 的 GitHub 账号永远不会撞上 sub 为 `"4001"` 的 Google 用户。 |
| **会话** | 服务端会话记录，用户可自行列出并单个或全部吊销。 |
| **MFA** | TOTP，密钥加密存储，带重放水位线，一个验证码在有效窗口内不能用第二次。 |
| **密码生命周期** | 邮件令牌重置、管理员建号后的强制初始化，改密时全量吊销凭证。 |
| **OIDC 提供方** | 发现文档、JWKS、authorize、token、userinfo、RP 发起的登出，以及客户端注册与管理。 |
| **RBAC** | 角色、权限、分配与校验 —— 管的是 SoulAuth 自己的管理面。 |
| **暴力破解防护** | 账号维度与 IP 维度的锁定，阈值可调，外加按路由限流。 |
| **审计** | 每个安全相关动作都留痕，仪表盘、活动汇总与安全报告都是端点。 |

合计 **八个模块 74 个 HTTP 端点**，完整清单见 [API 参考](/zh/reference/api)。

## 别人能拿它干什么

凡是你本来会去买一个托管身份服务、但又想把身份数据留在自己手里的场景，
SoulAuth 都适用。

### 一套真正属于你的登录系统

最常见的情形。你有一个或几个应用，想让用户注册、登录、重置密码、开双因素 ——
既不想把用户数据交给第三方，也不想自己从一堆 crate 攒一套出来。
把应用指向 SoulAuth 的 OIDC 端点，就完了。

### 多个自有服务之间的单点登录

因为 SoulAuth 是真的 OIDC 提供方，多个应用可以共用一份身份。用户登录一次，
每个应用拿到针对同一 subject 的各自的 ID Token。
登出通过 `sid` claim 与 RP 发起的登出端点协同完成。

### AI 智能体 / 自动化系统的后端

这是 SoulAuth 被造出来的场景，也塑造了它的设计。当软件代替人采取行动时，
「这件事是谁授权的」不再是登录问题，而是**举证问题**。SoulAuth 的审计轨迹为每个
凭证事件记录*谁*和*何时*；它签发的短寿命、可本地验签的 ID Token，
让下游系统能证明某个动作归属于哪个人类主体 —— 而那个系统本身不持有任何凭证。

### 网关背后的身份提供方

SoulAuth 只发令牌，它不想当你的 API 网关。把它放在网关后面：网关对着 JWKS
端点校验 ID Token（首次取密钥之后，每个请求都不再有网络调用），
再把验过的 subject 往下游转发。

## SoulAuth 不是什么

把边界说清能省下大量接入时间：

- **不是你业务规则的授权服务器。** 它的 RBAC 管的是 SoulAuth 自己的管理 API ——
  每条权限都带 `soulauth:` 前缀正是为此。你应用的权限属于你的应用。
- **不是面向用户的界面。** SoulAuth 是 API。登录页、授权同意页、账号设置页
  都要你自己写（用 `LOGIN_PAGE_URL` 告诉 SoulAuth 你的登录页在哪）。
- **不是多租户 SaaS 控制面。** 没有租户模型，也没有组织模型。
  需要的话，它在 SoulAuth 之上，不在里面。
- **不是目录服务。** 没有 LDAP，没有 SCIM，没有用户组同步。
- **不是完整的 OAuth 2.0 授权服务器。** SoulAuth 用授权码流程做**认证**。
  客户端凭证模式、设备码、面向第三方 API 的资源 scope 都不在范围内。

## 为什么是 Rust、一个二进制、一个数据库

运维面被刻意压到最小。没有消息队列，没有缓存层，没有 sidecar。
SoulAuth 只要一个 SurrealDB 实例和四个环境变量就能启动 ——
而如果你把它指向一个公网地址却没配那几把「让令牌活过重启」的密钥，
它会**拒绝启动**，见[生产闸门](./deployment#生产闸门)。

所有本来会变成运行期惊喜的东西，都被前移成了启动期失败。

## 它有多成熟

SoulAuth 是 1.0 之前的版本，这一点不打算含糊。已有的部分是测过的：
131 个单元测试、313 条跑在真实服务与真实数据库上的集成断言，
外加一个把文档里的安装步骤从头到尾执行一遍的部署走查脚本 ——
文档要是和现实分叉了，CI 会先发现。

已知的缺口与被接受的风险列在
[`SECURITY.md`](https://github.com/RcityHarold/SoulAuth/blob/main/SECURITY.md)
里，不留给你自己去踩。
